\section{Bonus 的结果与分析}
\label{sec:bonus}

附加题有两条相互独立的规模轴：500,000 个文件主要压测构建侧和文档表，400,000,000 个
不同词主要压测词典与 posting。项目分别实现了 SPIMI 式块式构建、磁盘 B+ 树词典和
v2 差分压缩，并完成了能够实际运行的规模实验。% src: F11–F15

\subsection{规模边界与实测范围}

按本轮 500,000 文档合成语料的实测锚点，4,908,747 个词项的整份内存索引峰值 RSS 为
2.00 GiB。若只按词项数线性放大到 4 亿词，峰值将达到约 160 GiB，普通单机无法容纳。
因此全内存构建不能直接回答附加题。% src: F15；160 GiB 为线性外推

500,000 文件这一轴已经实测完成：统计、块式构建和内存构建都在 16 GiB 机器上运行，
没有出现文件数导致的地址空间或文档表问题。400,000,000 个不同词没有端到端跑完，
查询侧用 B+ 树实测到 50,000,000 个键后外推，构建侧用块式构建的 490 万词实测和
$O(\text{预算})$ 内存上界说明扩展路径。报告会明确区分实测点与外推点。

\subsection{磁盘 B+ 树词典}

查询侧的问题不是如何查得更快，而是如何避免把完整 term 表读入内存。B+ 树 sidecar
把每个 term 映射到 posting 偏移和块长，查询一次只经过根到叶的若干页。本轮从 10 万
键实测到 5,000 万键，结果见表~\ref{tab:bptree-scale}。

\subsection{块式构建与 500,000 文档}

正式莎士比亚语料上，预算 4,096 的块式构建产生 17 个 run、峰值活词 5,129，临时 run
共 4,166,556 字节，产物与内存构建逐字节一致。% src: F22

500,000 文档实验把这条路径放大到实际小文件规模。合成语料包含 500,000 个文件、
20,000,000 个 token 和 4,908,747 个不同词。块式构建产生 4,855 个 run，扫描
5.47 秒、归并 125.08 秒，总墙钟 168.16 秒，峰值 RSS 1.01 GiB；全内存构建耗时
76.75 秒、峰值 RSS 2.00 GiB。两种方式生成的 v1 索引都是 427,603,247 字节，
SHA-256 相同。% src: F13、F15

块式构建把峰值内存几乎减少一半，但归并耗时明显增加。4,855 个 run 当前通过线性扫描
所有游标找最小词，成本约为 $O(T\cdot R)$；换成堆做 $k$ 路归并可以降到
$O(T\log R)$。这部分时间与临时空间是大规模构建必须付出的工程代价。

\subsection{v2 压缩结果}
\label{sec:compression}

v2 只改变 postings 段：docID 和 position 存差分，tf 与差分值使用字节对齐变长码。
主语料索引从 3,685,655 字节降到 1,725,694 字节，为 v1 的 46.82\%；构建耗时仍为
0.19 秒，查询输出不变。% src: F21

500,000 文档语料上，postings 段在总文件中占比只有 56.1\%，term 表成为主要体积来源，
所以整体压缩率不如主语料：v1 427,603,247 字节降到 v2 284,560,009 字节，为 v1 的
66.55\%。postings 段自身的压缩率约为 59.6\%，与主语料的 61.8\% 接近。% src: F13、F14

说明压缩并非在所有资源维度上都占优。

\subsection{Bonus 结论}

500,000 个文件这一轴已经实测通过；400,000,000 个不同词没有端到端运行。查询侧已经
把词典移到磁盘并把单次查询控制在常数页读，构建侧已经用块式构建去掉“内存随全词表
增长”的假设。完整的大规模系统还缺 SPIMI 归并与 B+ 树的直接集成、分布式分片与故障
恢复。现有结果支持“关键部件可扩展”的结论，但不支持“完整 4 亿词系统已经跑通”的说法。
